# Deploy DEV KRAKEN

Target: `devkraken-514023`, region `us-central1`, Cloud Run service `dev-kraken-api`, PostgreSQL database `kraken`, and a new GitHub repository `dev-kraken-portal`.

## 1. Repository and identity

Create the repository with `scripts/create-repository.sh` after `gh auth login`, or through GitHub. The helper defaults to a private source repository. Private-repository GitHub Pages requires an eligible GitHub plan. If the account lacks that entitlement, choose a public source repository explicitly or upgrade; never expose an existing private repository just to enable Pages.

Enable **Settings → Pages → Source → GitHub Actions**. Create a `production` GitHub environment. Protect `main` with required PR checks to make merges the normal production release path. The workflow also runs on a direct push to `main`, so branch protection matters.

## 2. Google Cloud infrastructure

Authenticate with an account permitted to manage the target project and verify billing is enabled. The provided local CLI installation, when present, is `.tools/google-cloud-sdk/bin/gcloud` (ignored by Git). Otherwise use a standard Google Cloud CLI installation.

```sh
gcloud auth login
gcloud auth application-default login
gcloud config set project devkraken-514023
```

Install Terraform >=1.6, then create ignored `infra/terraform.tfvars`:

```hcl
github_repository = "DiegoDkSanchez/dev-kraken-portal"
github_repository_id = "REPLACE_WITH_NUMERIC_REPOSITORY_ID"
```

Retrieve the ID with `gh api repos/DiegoDkSanchez/dev-kraken-portal --jq .id`.

```sh
terraform -chdir=infra init
terraform -chdir=infra plan -out=portal.tfplan
terraform -chdir=infra apply portal.tfplan
terraform -chdir=infra output
```

Review the plan before applying: Cloud SQL and storage incur charges. Cloud SQL deletion protection and seven-day point-in-time recovery are enabled. No public authorized database networks are configured; Cloud Run connects through its Cloud SQL attachment. Keep Terraform state private: it contains the generated database password. Use an access-controlled remote state bucket for shared administration; do not commit state, plans, tfvars, or credentials.

## 3. Email

Choose an SMTP provider and a verified sender address. Create a version of the `kraken-smtp-password` Secret Manager secret using stdin or the Google Cloud console. Do not commit the value or pass it in command-line arguments. The email password is available only to the API runtime service account.

Configure these GitHub repository or `production` environment variables:

| Variable | Value |
| --- | --- |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | Terraform `workload_identity_provider` output |
| `GCP_DEPLOYER_SERVICE_ACCOUNT` | Terraform `deployer_service_account` output |
| `RUNTIME_SERVICE_ACCOUNT` | Terraform `runtime_service_account` output |
| `CLOUD_SQL_CONNECTION` | Terraform `cloud_sql_connection` output |
| `GCP_REGION` | `us-central1` |
| `APP_URL` | `https://devkraken.xyz/portal` |
| `SMTP_ENABLED` | `true` after the secret is saved; default `false` deploys with email disabled |
| `SMTP_HOST` | Your provider's SMTP host |
| `SMTP_PORT` | `587` or `465` |
| `SMTP_USER` | Your SMTP username |
| `MAIL_FROM` | Verified sender, e.g. `DEV KRAKEN <portal@your-domain.com>` |

With `SMTP_ENABLED=false`, the API and frontend deploy, but estimate sending, invitations, and owner bootstrap remain unavailable. After saving the secret, set `SMTP_ENABLED=true` and rerun deployment.

The database password is generated by Terraform and stored in `kraken-db-password`. The SMTP password remains in Secret Manager. No GCP JSON key is required: OIDC is constrained to this repository's immutable numeric ID and the `main` ref.

## 4. Deploy

Commit the application, lockfile, workflows, and infrastructure. Push/merge to `main` or run **Deploy DEV KRAKEN** from GitHub Actions. The pipeline fails early if required variables are absent. Schema migrations run under an advisory lock on API startup. They are additive and idempotent for this initial schema.

The API is public at the Cloud Run transport layer so browsers can reach it. All application data routes require authentication and authorization; only health, login, invitation acceptance, and token-scoped approval endpoints are public. CORS is restricted to the origin derived from APP_URL. The frontend contains no database or SMTP credentials.

## 5. Invite the owner once

After deployment, use a one-off Cloud Run job with the same image, runtime service account, Cloud SQL attachment, environment variables and secrets as the API, replacing its command with `node src/bootstrap.js`:

```sh
# Set these from Terraform outputs and your SMTP settings first:
# PROJECT_ID, REGION, CLOUD_SQL_CONNECTION, RUNTIME_SERVICE_ACCOUNT,
# APP_URL, SMTP_HOST, SMTP_PORT, SMTP_USER, MAIL_FROM, IMAGE
node scripts/cloud-env.mjs > /tmp/kraken-env.yaml
gcloud run jobs create dev-kraken-bootstrap \
  --project=devkraken-514023 --region=us-central1 \
  --image="$IMAGE" --service-account="$RUNTIME_SERVICE_ACCOUNT" \
  --set-cloudsql-instances="$CLOUD_SQL_CONNECTION" \
  --set-secrets=PGPASSWORD=kraken-db-password:latest,SMTP_PASSWORD=kraken-smtp-password:latest \
  --env-vars-file=/tmp/kraken-env.yaml \
  --command=node --args=src/bootstrap.js --max-retries=0
gcloud run jobs execute dev-kraken-bootstrap \
  --project=devkraken-514023 --region=us-central1 --wait
```

The job sends the first invitation to `diegodksanchez@gmail.com`. Complete it, then invite partners through **Team & access**. Once an administrator exists the bootstrap command refuses to create another. Remove the bootstrap job after successful setup if desired.

## Production verification

- API `/api/health` returns `{ "status": "ok" }`.
- Owner can sign in through Pages.
- Invite a client and developer to a test project.
- Send an estimate; verify receipt and PDF, approve it as the client, then activate it as admin.
- Add a ticket, comment, and asset; verify developer can move states but cannot access estimates.
- Verify a second client cannot see the first client's project.
- Confirm merge-to-main deployment and Cloud SQL backups.

## Operations

Re-deploy a known-good commit for application rollback. Database rollback requires a separate migration or PITR; do not run a destructive schema rollback automatically. Watch Cloud Run error logs and Cloud SQL connection/storage metrics. Increase Cloud SQL tier and availability for production load; keep max Cloud Run instances and pool sizes within the database connection budget (default up to 3 instances × 10 connections).

Reference documentation: [Angular compatibility](https://angular.dev/reference/versions), [Cloud Run with Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connect-instance-cloud-run), [GitHub Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Monorepo Pages hosting

The `dev-kraken-portal` repository owns the `devkraken.xyz` custom domain, with GitHub Actions as its Pages source. Pages is disabled in the former `dev-kraken-web` repository; retain that repository for history. Existing GitHub Pages DNS records continue to apply because the account and hosting provider are unchanged. Enable HTTPS enforcement after GitHub provisions the domain certificate.

The deployment builds Angular with `/portal/` as its base href, copies only public landing files to `dist/pages/`, and places Angular output in `dist/pages/portal/`. The API remains on Cloud Run. Set the production environment variable `APP_URL=https://devkraken.xyz/portal`; the deployment derives CORS origin `https://devkraken.xyz` and email links from it. Hash-based invitation and approval links work without a Pages SPA rewrite.

### Email deliverability

Production SMTP requires TLS (port 465 or STARTTLS). Set optional `MAIL_REPLY_TO` in the GitHub production environment to a monitored mailbox. Verify SPF, DKIM, and DMARC with the SMTP provider; see [email delivery documentation](doc/email-deliverability.md) for current measures and verification steps.
